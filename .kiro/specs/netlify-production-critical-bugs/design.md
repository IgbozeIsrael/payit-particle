# Netlify Production Critical Bugs - Bugfix Design

## Overview

This bugfix addresses two critical production failures in the PayIT mobile application deployed on Netlify:

**Bug 1 - Magic Link Authentication Bypass**: The authentication system bypasses Magic.link SDK entirely, generating mock tokens (`payit_email_${email}`, `dev_magic_token_${timestamp}`) instead of real DID tokens. This prevents user authentication in production.

**Bug 2 - Historical Data Exclusion**: Database queries use restrictive AND conditions that filter out pre-migration user records, causing users who existed before database schema changes to lose access to their deposits and transaction history.

**Bug 3 - Missing Helper Functions**: Critical helper functions (`parseJsonBody`, `getAllUserAddresses`, `findUserByAllIdentifiers`) are called but not defined, causing endpoint crashes.

These bugs block production authentication and cause data loss for historical users. The fix implements proper Magic.link integration, inclusive database queries with OR conditions across all user identifiers, and adds the missing helper functions.

---

## Glossary

- **Bug_Condition (C)**: The conditions that trigger the bugs - production authentication requests, queries for pre-migration users, or calls to undefined helper functions
- **Property (P)**: The desired behavior - real Magic.link DID tokens, inclusive data retrieval across all user identifiers, and defined helper functions
- **Preservation**: Existing behavior for non-buggy inputs (new users, development mode, valid endpoints) must remain unchanged
- **DID Token**: Decentralized Identifier token generated by Magic.link SDK with format `did:ethr:0x...`
- **Mock Token**: Fake tokens with format `payit_email_${email}` or `dev_magic_token_${timestamp}` that cannot be validated
- **Pre-migration User**: A user who exists in the database with historical deposits/transactions but whose `user_id`, `deposit_address`, or identifier fields changed during schema migrations
- **Inclusive Query**: Database query using OR conditions to match ANY of a user's possible identifiers rather than requiring ALL to match
- **Magic SDK**: Magic.link JavaScript SDK that handles passwordless authentication via email magic links
- **mobile-api.js**: Backend Express-style API handler file (~3000 lines) located at `src/mobile-api.js` in payit-particle workspace

## Bug Details

### Bug Condition 1: Magic Link Mock Token Generation

The bug manifests when a production user attempts to authenticate via email magic link. The backend endpoint `/api/mobile/auth/send-magic-link` (line 166 of mobile-api.js) returns a mock token instead of triggering the Magic.link SDK to send a real authentication email.

**Formal Specification:**
```
FUNCTION isMockTokenBug(input)
  INPUT: input of type AuthenticationRequest
  OUTPUT: boolean
  
  RETURN (input.environment = 'production' OR input.environment = 'staging')
         AND (input.token_generated MATCHES 'payit_email_*' 
              OR input.token_generated MATCHES 'dev_magic_token_*')
         AND NOT magic_sdk_invoked(input)
END FUNCTION
```

### Examples

- **Production Auth - CURRENT**: User enters `user@example.com` → Backend returns `{ token: 'payit_email_user@example.com' }` → Frontend stores invalid token → Authentication fails
- **Production Auth - EXPECTED**: User enters `user@example.com` → Backend calls `magic.auth.loginWithEmailOTP(email)` → Magic.link sends email → User clicks link → Frontend retrieves valid DID token `did:ethr:0xABC...` → Backend validates token → User authenticated

---

### Bug Condition 2: Historical Data Exclusion via Restrictive Queries

The bug manifests when querying balance or transaction data for users who existed before database migrations. Queries use AND conditions requiring BOTH `deposit_address` AND `user_id` to match, filtering out historical records where these values differ.

**Formal Specification:**
```
FUNCTION isHistoricalDataBug(input)
  INPUT: input of type UserDataQuery
  OUTPUT: boolean
  
  RETURN input.user.has_pre_migration_records = true
         AND (input.query_uses_AND_on_identifiers = true
              OR input.query_checks_only_telegram_id = true
              OR input.query_missing_mobile_auth_id = true)
         AND historical_deposits_exist(input.user)
         AND query_result_excludes_historical_data(input)
END FUNCTION
```

### Examples

- **Balance Query for Pre-migration User - CURRENT**: 
  - User has deposits with `deposit_address = 0xOLD123` and `user_id = alice@legacy.com`
  - After migration: user's `personal_smart_account = 0xNEW456` and `mobile_auth_id = did:ethr:0xABC`
  - Query: `WHERE deposit_address = '0xNEW456' AND user_id = 'did:ethr:0xABC'`
  - Result: 0 deposits found (historical data excluded)
  
- **Balance Query for Pre-migration User - EXPECTED**:
  - Query: `WHERE deposit_address IN ('0xOLD123', '0xNEW456', ...) OR user_id IN ('alice@legacy.com', 'did:ethr:0xABC', ...)`
  - Result: All historical deposits + new deposits retrieved

- **Transaction History - CURRENT**: Pre-migration user sees empty transaction list despite having historical transfers
- **Transaction History - EXPECTED**: User sees complete history including all pre-migration transactions

---

### Bug Condition 3: Missing Helper Functions

The bug manifests when endpoints call helper functions that are referenced in the code but never defined, causing immediate crashes.

**Formal Specification:**
```
FUNCTION isMissingHelperBug(input)
  INPUT: input of type CodeExecution
  OUTPUT: boolean
  
  RETURN input.function_name IN ['parseJsonBody', 'getAllUserAddresses', 'findUserByAllIdentifiers']
         AND function_definition_missing(input.function_name)
         AND endpoint_invoked(input)
END FUNCTION
```

### Examples

- **parseJsonBody - CURRENT**: Line 169 calls `await parseJsonBody(req)` → ReferenceError: parseJsonBody is not defined → Endpoint crashes
- **parseJsonBody - EXPECTED**: Function defined at top of mobile-api.js → Successfully parses request body → Endpoint continues

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Development mode authentication with fallback tokens must continue to work for local testing
- New users with consistent identifiers must continue to have their data retrieved correctly
- Existing database helper functions (`getUser`, `getProfile`, `getProfileByType`) must continue to work as before
- Non-authentication endpoints must continue to function identically
- Balance calculations, currency conversions, and transaction formatting must remain unchanged

**Scope:**
All inputs that do NOT involve production authentication attempts, pre-migration user queries, or calls to the three missing helper functions should be completely unaffected by this fix. This includes:
- Local development authentication flows
- New user registration and account provisioning
- All other API endpoints beyond `/api/mobile/auth/send-magic-link`, `/api/mobile/me`, `/api/mobile/balance`, `/api/mobile/transactions`
- Database queries for users with consistent post-migration identifiers

## Hypothesized Root Cause

Based on the bug description and code analysis, the most likely issues are:

1. **Incomplete Magic.link Integration**: The backend endpoint `/api/mobile/auth/send-magic-link` was scaffolded to return mock tokens for rapid development but never completed with actual Magic SDK calls. The `magicService` module likely exists but isn't properly invoked in the production code path.

2. **Migration Script Oversight**: A database migration changed identifier field names (e.g., `telegram_id` → `user_id`, added `mobile_auth_id`, split smart accounts into `personal_smart_account` and `business_smart_account`) but query logic wasn't updated to check all possible identifier variants using OR conditions.

3. **Helper Function Implementation Gap**: The three helper functions were likely planned as refactoring tasks (extracting common logic into reusable functions) but the implementation was never completed, leaving function calls in place that reference undefined functions.

4. **Environment Variable Configuration**: The Netlify deployment may be missing the `MAGIC_SECRET_KEY` environment variable, causing Magic SDK initialization to fail silently and fall back to mock token generation.

5. **Query Logic Copy-Paste Error**: Balance and transaction queries appear to have been copied from a code example that used restrictive AND conditions for security, but this pattern excludes legitimate historical data when user identifiers change across migrations.

_For any_ request that does NOT trigger the bug conditions (production auth attempts, pre-migration user queries, or undefined function calls), the fixed mobile-api.js SHALL produce exactly the same behavior as the original code, preserving all existing functionality for development mode authentication, new user queries, and all other endpoints.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8, 3.9, 3.10**

### 1. **Add Missing Helper Functions** (Lines 1-30)

Add three helper function definitions immediately after the existing helper functions (after `getOrProvisionReceiveMethods`):

```javascript
// Helper: Safely parse JSON request body
async function parseJsonBody(req) {
  return new Promise((resolve, reject) => {
    let body = '';
    req.on('data', chunk => body += chunk.toString());
    req.on('end', () => {
      try {
        resolve(body ? JSON.parse(body) : {});
      } catch (e) {
        resolve({});
      }
    });
    req.on('error', () => resolve({}));
  });
}

// Helper: Get all addresses associated with a user
function getAllUserAddresses(user) {
  const addresses = new Set();
  if (user.personal_smart_account) addresses.add(user.personal_smart_account);
  if (user.business_smart_account) addresses.add(user.business_smart_account);
  if (user.owner_address) addresses.add(user.owner_address);
  return Array.from(addresses).filter(Boolean);
}

// Helper: Find user by checking all possible identifier fields
function findUserByAllIdentifiers(identifier, db) {
  const cleanId = (identifier || '').trim().toLowerCase();
  if (!cleanId) return null;
  
  const stmt = db.prepare(`
    SELECT * FROM users 
    WHERE LOWER(COALESCE(user_id, '')) = ?
       OR LOWER(COALESCE(telegram_id, '')) = ?
       OR LOWER(COALESCE(mobile_auth_id, '')) = ?
       OR LOWER(COALESCE(owner_address, '')) = ?
       OR LOWER(COALESCE(personal_smart_account, '')) = ?
       OR LOWER(COALESCE(business_smart_account, '')) = ?
       OR LOWER(COALESCE(email, '')) = ?
       OR LOWER(COALESCE(business_email, '')) = ?
    LIMIT 1
  `);
  return stmt.get(cleanId, cleanId, cleanId, cleanId, cleanId, cleanId, cleanId, cleanId);
}
```

**Rationale**: These functions extract common patterns used throughout mobile-api.js. `parseJsonBody` safely handles request body parsing. `getAllUserAddresses` centralizes address collection logic. `findUserByAllIdentifiers` implements comprehensive user lookup that checks all possible identifier columns.

```javascript
        telegramId,
        user?.user_id,
        user?.telegram_id,
        user?.mobile_auth_id
      ])).filter(Boolean);
      
      const userPH = userIds.map(() => '?').join(',');
      const addrPH = allAddresses.map(() => '?').join(',');
      
      // ✅ INCLUSIVE OR QUERY WITH ALL IDENTIFIERS AND ADDRESSES
      const stmt = db.db.prepare(`
        SELECT * FROM hd_deposits 
        WHERE user_id IN (${userPH})
           OR deposit_address IN (${addrPH})
           OR virtual_account_no IN (
               SELECT nuvion_account_no 
               FROM accounts 
               WHERE profile_id = ? OR user_id IN (${userPH})
           )
        ORDER BY created_at DESC LIMIT 30
      `);
      const deposits = stmt.all(...userIds, ...allAddresses, profId, ...userIds);
      
      deposits.forEach(dep => {
        formattedTxs.unshift({
          id: dep.deposit_id,
          name: 'Bank Deposit',
          type: 'INFLOW',
          date: new Date(dep.created_at || Date.now()).toLocaleString(),
          amount: `+${dep.currency === 'NGN' ? '₦' : '$'}${dep.expected_amount} ${dep.currency || 'USDT'}`,
          raw_amount: dep.expected_amount,
          currency: dep.currency || 'USDT',
          isNegative: false,
          status: 'completed',
          reference: dep.deposit_id,
          sender: dep.virtual_account_no ? `Nuvion Virtual Account #${dep.virtual_account_no}` : 'External Bank Transfer',
          recipient: user.first_name ? `${user.first_name} ${user.last_name || ''}`.trim() : (user.business_name || 'PayIT Wallet'),
          bank_name: 'VFD Microfinance Bank / Nuvion',
          note: 'Direct Bank Deposit to PayIT Wallet'
        });
      });
    } catch (_) {}

    return sendJson(res, 200, { transactions: formattedTxs });
  } catch (e) {
    return sendJson(res, 500, { error: e.message });
  }
}
```

**Rationale**: Similar to balance query fix - use `getAllUserAddresses()` helper and build comprehensive lists of all user identifiers and addresses. Query uses OR conditions to match ANY of these values, ensuring historical transactions are included.
